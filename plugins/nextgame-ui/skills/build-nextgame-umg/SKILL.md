# Build NextGame UMG

Create prototype or explicitly authorized formal UMG assets. Treat image interpretation, component selection, layout planning, Editor mutation, and validation as separate stages so project-specific components and standards can evolve without changing the workflow.

## Required inputs

- Accept an approved `UIRequirementSpec 0.1`, a legacy `UILayoutSpec 0.2`, or raw reference images plus user text.
- When the input is raw references, use the sibling `$analyze-nextgame-ui-requirements` skill first. Its review gate is mandatory during the initial rollout; return the review summary and do not connect to or modify Unreal until the user accepts it.
- When the input is a `UIRequirementSpec`, read [requirement-build-handoff.md](references/requirement-build-handoff.md), validate it against its RequestPacket, and require the current `revision`, `reviewGate.status: accepted`, and `approvedContentSha256` before producing layouts or a build bundle.
- Keep direct `UILayoutSpec 0.2` input as a backwards-compatible expert path. It does not acquire requirement semantics that are absent from the file.
- Treat a requirement-driven production build as the formal Multi-Agent path. After verification, capture normalized actual Unreal readback, present the concrete build result to the user, and end that turn. Do not immediately invoke `$document-nextgame-umg`.
- A later direct user message must explicitly accept the presented UMG result before the primary coordinating Agent creates and validates `ui-build-acceptance.json` and starts documentation. The original full-flow request and the earlier requirement approval cannot pre-authorize this result gate.
- Do not generate a formal program-facing UMG explanation document or `ui-build-acceptance.json` for prototype builds or a legacy standalone `UILayoutSpec 0.2`. An explicit user request to omit documentation also ends the production task after the verified build-result presentation without invoking the documentation stage.
- Obtain an asset name when the user supplied one. Otherwise derive a concise `umg_ai_<purpose>` name for prototype mode.
- For every complete NextGame project screen (`profile.assetKind: screen`), use the fixed project design canvas `2560x1440`. Treat the source image size only as measurement input and remap its normalized geometry to the project canvas.
- For child widgets and non-project prototypes, use the local functional or actual image dimensions. If neither is available, use `1920x1080` and disclose the assumption.
- Apply the basename guard to the Widget Blueprint actually being mutated before executing the Designer `Screen Size` decision. In prototype mode this is `asset.name`; `profile.targetAsset` remains future-target metadata and cannot override it. In production/formal lowering prefer `profile.targetAsset.name` and fall back to `asset.name`. Every resolved `umg_*` basename uses `FillScreen`, and explicit `Desired` is invalid; a missing mode in an archived layout remains readable and resolves through the same hard rule. Only a resolved `uw_*` basename may execute analyzed `Desired` or `FillScreen`; a missing or unclear `uw_*` decision falls back to `FillScreen`. Unknown or legacy basenames also use conservative `FillScreen`. `assetKind` and directory alone do not choose the mode. A `Desired` UILayoutSpec must additionally prove non-zero root Desired Size through at least one root-direct child with either a point-anchored Canvas Slot whose `autoSize` is false and whose `right` and `bottom` sizes are positive, or a measured content-driven record containing `verified: true`, positive two-axis `measuredDesiredSize`, and a valid `evidenceId`. An empty root, an auto-sized fixed Slot, a verified-only claim, or zero-offset full-stretch content is invalid. The stricter list-entry first-Panel size contract still applies. `DesiredOnScreen`, `Custom`, and `CustomOnScreen` are not substitutes, and `DesignTimeSize` is not the `referenceSize` contract.
- Use `mode: prototype` and `/Game/UI/AIPrototype` for exploratory work.
- Use `mode: production` only when the user explicitly requests creation in the formal UMG folder. Require the actual `asset` destination to exactly match the validated `profile.targetAsset`.
- Never overwrite an existing asset unless the user explicitly authorizes updating that exact asset.
- Read [common-widget-rules.md](references/common-widget-rules.md) for every UMG task. Apply its runtime-variable, even-font-size, passive hit-testing, explicit wrapping-width, text-justification, flow/scroll Slot, complete-image composition, and localization-adaptation rules across all systems.
- Read [protected-stretch-and-state-defaults.md](references/protected-stretch-and-state-defaults.md) for every UMG task. Preserve accepted screen-expanding protected regions through the complete Slot chain, and initialize visual-state families with the unselected branch visible while project code owns every alternate state.
- Read [project-layout-rules.md](references/project-layout-rules.md) whenever `profile.assetKind` is `screen`. Apply the `2560x1440` complete-screen canvas, per-axis decorative adaptation, and full-canvas verification contract.
- Read [project-ui-rules.md](references/project-ui-rules.md) whenever the task has an intended project Widget Blueprint name or path. Apply it as the complete asset naming and placement contract.
- Read [widget-component-naming.md](references/widget-component-naming.md) before naming nodes inside any WidgetTree. Keep these component instance rules separate from Widget Blueprint asset naming.
- Read [region-module-structure.md](references/region-module-structure.md) before interpreting visual groups or building a WidgetTree hierarchy. Keep region structure separate from both naming rule sets.
- Read [text-component-content.md](references/text-component-content.md) whenever the interface contains text. Split independent text bounds into separate TextBlocks and keep icons or decoration out of text content.
- Read [dynamic-list-widgets.md](references/dynamic-list-widgets.md) whenever runtime data controls the number of linear or tiled entries. Keep the collection module and entry Widget Blueprint separate, record their relationship in the spec, and materialize each entry referenceSize in its first structural Panel Slot.
- Read [component-knowledge.md](references/component-knowledge.md) whenever selecting or configuring `LuaListView`, `LuaTileView`, `SizeBox`, `GameScrollBox`, or another project component documented there. Do not add a SizeBox solely to establish a list-entry root size.
- Read [shared-widget-reuse.md](references/shared-widget-reuse.md) before planning any new project child-widget, list-entry, or runtime-template asset. Only active shared entries are executable. Model the chain as shared prototype, system-specific Class Settings Parent Class child, independent inherited `NamedSlot("SlotDown")`/`NamedSlot("SlotUp")` content records, and later host nesting/EntryClass; keep parameter overrides, Lua inheritance, and dynamic loading separate.
- For every non-fight project system, read [standard-system-ui.md](references/standard-system-ui.md) and use its screen, region, child-widget, and screen-local collection ownership model. Fight remains the stricter exception governed by `fight-ui.md`.
- Set `profile.assetKind` to `prototype`, `screen`, or `child-widget`. For a project-target screen or child widget, also set `profile.system`, `profile.systemFolder`, optional naming segments, and `profile.targetAsset`.
- Set `profile.designSizeMode` explicitly on every new layout. For a requirement-driven `uw_*` layout, copy the accepted per-asset analysis decision exactly. For an `umg_*` target, require `FillScreen` even if the accepted analysis decision says `Desired`; treat that conflict as invalid input rather than lowering it. Do not derive the mode from `profile.assetKind` or directory alone.
- For a new project system, make `profile.systemFolder` identify the same system as `profile.system`, target the screen directly under `/Game/UI/UMG/<SystemFolder>`, and target child widgets under its `Widgets` subfolder.
- When `profile.system` is `fight`, read [fight-ui.md](references/fight-ui.md), use `/Game/UI/UMG/Fight/umg_fight` as the reference, and never substitute `umg_fight1`.

## Workflow

### 0. Enforce the requirement gate

- Classify the input before any Editor connection: raw sources, `UIRequirementSpec 0.1`, or legacy `UILayoutSpec 0.2`.
- For raw sources, invoke `$analyze-nextgame-ui-requirements` with the original images, user wording, applicable project rules, and named reference assets. Stop after it writes a pending requirement and presents the module list, state matrix, assumptions, and questions for user review.
- For a requirement input, run `python ../analyze-nextgame-ui-requirements/scripts/validate_requirement_spec.py <ui-requirement.json> --request-packet <request-packet.json> --check-findings-files`. Require this strict pass to load and validate all nine AgentFindings and their recorded contexts and to prove complete alias/discard coverage of local IDs. Reject a pending or rejected review gate, stale findings/context/input digests, an approval digest mismatch, unresolved high-impact or `blocksBuild` decisions, an unresolved/empty formal target, a region/element parent cycle, or duplicate element state assignments.
- Use only accepted claims, states, assets, and decisions when planning the build. Preserve proposed, rejected, and unresolved material in the requirement file without lowering it into WidgetTree nodes.
- Before creating a planned child-widget, list-entry, or runtime-template target, check the current SystemFolder and the validated shared registry for a compatible active asset. Never execute a registry candidate or create a duplicate for a selected same-purpose shared control. A brand-new project-common layout asset may use the narrowly scoped Bundle-local `planned-bootstrap` contract in [shared-widget-reuse.md](references/shared-widget-reuse.md); an existing asset may not and must first obtain real Unreal identity readback. A new common candidate must acquire and verify two root-direct, full-fill, Auto Size disabled, variable NamedSlots with `SelfHitTestInvisible`: `SlotDown` first with ZOrder strictly below every other root direct sibling, and `SlotUp` last with ZOrder strictly above every other root direct sibling. New shared assets may add this pair directly; existing assets must preserve every observed legacy NamedSlot and saved binding, using live readback rather than assuming a universal `Slot1`. Never name a NamedSlot exactly `Slot`: `/Script/UMG.Widget` already exposes a reflected `Slot` property and the Widget Blueprint will not compile. A system consumer uses a Parent Class child; classify additive content by lower/upper draw layer, then give each used inherited Slot exactly one direct semantic Panel. Both Slots stay empty when no additive content exists, and both may be used when both layers are required. Express the chain with validated `UIBuildBundle 0.3` reuse relations; Bundle 0.2 remains closed historical compatibility. If the relation cannot be represented, stop before Editor connection instead of duplicating the control.
- Create the task workspace at `Saved/CodexUIRequirements/<request-id>/`; keep the accepted requirement, generated layouts, bundle, logs, and verification evidence together.

### 1. Interpret the image

- When an accepted requirement is available, treat its accepted region, element, data, responsive, state, and asset models as authoritative. Consult source images only for evidence or geometry already referenced by that requirement; do not silently reinterpret accepted state or asset decisions.
- Inspect the attached image directly.
- Identify top-level and nested semantic regions before leaf controls. Use shared frames, headers, alignment, proximity, repeated layout, shared purpose, and independent anchoring as grouping evidence.
- Choose one appropriate region container for every clearly recognized group. Do not flatten those controls into unrelated direct children of the root.
- For standard non-fight systems, use ordinary semantic Panels and screen-local LuaListView/LuaTileView by default. Do not extract a `uw_*` merely for cohesion, self-contained state, or visual complexity; require an evidenced data-entry, explicit runtime-template, proven cross-screen reuse, or user-requested reusable boundary. Fight remains the integration-shell exception.
- Identify repeated elements, text, approximate colors, interactive controls, progress indicators, and likely hierarchy inside each region.
- Distinguish fixed repeated decoration from a runtime-variable collection. When repeated entries share one visual structure and differ only by loaded text, numbers, images, state, or other data, treat them as a data-driven collection by default even if the reference currently shows a fixed count. Mark it with `profile.listRole: container` and use `LuaListView` or `LuaTileView` instead of statically authored rows. Only keep repeated rows static when they are genuinely fixed decoration or the accepted requirement explicitly requires individually authored content.
- For every runtime collection, decide its overflow contract from the feature requirement and record `profile.collectionSizing` as `show-all` or `fixed-viewport`. Do not equate dynamic count with scrolling.
- Identify each independently bounded text block. Create separate text nodes for separate titles, rows, labels, counts, or items.
- Choose an even font size for every text node. For text that may wrap, determine a concrete positive `Wrap Text At` width and plan for longer localized content.
- Choose `Left`, `Center`, or `Right` justification for every TextBlock from its visual alignment, fixed boundary, and safe growth direction. Do not rely on the engine default.
- Decide which nodes actually receive input. Treat every other component as passive and plan `Not Hit-Testable (Self Only)` visibility.
- Decide which nodes project code must directly read, modify, populate, show, hide, or otherwise control at runtime. Mark those nodes `isVariable: true`; leave fixed labels, separators, backgrounds, frames, and other static decoration false or omitted.
- Represent icons, markers, separators, backgrounds, and decorative lines with `visual.image` nodes, which map exclusively to `/Script/UIFramework.GameImage`. Keep the `Img` instance prefix and never create native `/Script/UMG.Image` widgets in new assembly work. Do not encode graphics as Unicode text glyphs or repeated text characters.
- Lower every accepted static visual inventory item to a compatible visual node. Do not use a semantic region Panel, an empty entry root, or a `generated-support` mapping as proof that a backplate, frame, separator, accent, marker, or icon art exists. If the project has no matching resource, preserve the node and apply the accepted temporary resource or pure-color placeholder.
- Treat every click, tap, and discrete state-switch target as Button-owned interaction. Add an `input.button` named with the `Btn` prefix over the complete effective hit area; keep child Panels, GameImages, and TextBlocks passive. Do not add EventGraph or business switching logic. Continuous slider dragging and collection/scroll navigation retain their specialized input components.
- Prefer approximate geometry over clarification. Ask only when the target purpose or destructive destination is ambiguous.
- Express rectangles as normalized `[x, y, width, height]` values in the `0..1` range.
- For a complete screen, normalize source-image measurements first and author them against the complete `2560x1440` project canvas. Do not retain the source pixel size as an inner frame.
- For every adaptive Canvas child, reason about horizontal and vertical behavior independently: left, center, right, or stretch on the horizontal axis; top, center, bottom, or stretch on the vertical axis. Record that decision as `adaptiveLayout` when the node participates in screen adaptation.
- Infer anchors from semantic content gravity and protected composition areas as well as geometric proximity. Keep left-oriented modules attached to the left and right-oriented modules attached to the right when a wider viewport should reveal more of the central model, map, or other protected content.

### 2. Write and validate UILayoutSpec

- For an accepted requirement without shared reuse relations, have one build-planning Agent emit one `UILayoutSpec 0.2` per accepted asset plus one `UIBuildBundle 0.1`. Use `UIBuildBundle 0.3` for new shared extension, Class Settings Parent Class, or WidgetTree instance relations; Bundle 0.2 is accepted only for archived single-Slot artifacts. Reuse-only assets with no owned WidgetTree do not receive fake UILayoutSpec roots. Do not let parallel Agents write competing authoritative trees or IDs.
- Preserve accepted requirement IDs in the bundle's `nodeMappings` and dependency graph. Cover every accepted in-scope asset, region, element, collection, runtime field, responsive intent, state, and acceptance criterion; keep other entities explicitly out of scope in the requirement rather than fabricating mappings.
- For a screen asset, lower each accepted screen-space region and element bound into the corresponding UILayoutSpec `rect` unchanged. A child asset's local `referenceSize` defines only its internal coordinate space; it must never be used to infer, widen, shrink, or otherwise replace that child instance's screen host rectangle.
- Read [layout-spec.md](references/layout-spec.md) before creating a spec.
- Use UILayoutSpec version 0.2 and [ui-layout-spec.schema.json](assets/ui-layout-spec.schema.json) as the structural contract.
- Set `profile.explicitPanelSlots: true` on every newly planned layout. When the accepted Requirement enables `explicitPanelSlotsRequired`, copy each element `panelSlotIntent` exactly onto its mapped direct child: `flow` becomes `flowSlot`, `scroll` becomes `scrollSlot`, and the mapped parent must use the accepted `layoutRole`. For a `widget-tree-instance` realization, carry the same decision in `placementContract.slot` (`HorizontalBox`/`VerticalBox` plus Box Size, or `GameScrollBox`) and reference both child and immediate parent requirement elements. A reuse-only Parent Class child under a flow Box uses `childSizingCompatibility.mode: inherited-reuse-only-flow-slot`; pair Auto with `allocation`/`sizingStrategy: content-driven`, or weighted Fill with `allocation`/`sizingStrategy: weighted-remaining-space`. Under GameScrollBox use `inherited-reuse-only-scroll-slot` plus `sizingStrategy: scroll-slot`, no Box Size field, and preserve the reviewed Padding/alignments. Do not reuse `fill-host` for weighted or scroll allocation. Every generated support child under these parents still gets an explicit Slot. Archived 0.2 layouts without the profile flag remain readable but are not templates for new production.
- Use only roles present in [component-catalog.json](references/component-catalog.json).
- Name every node using its catalog `namePrefix` when one is present. Do not invent prefixes for roles without a supplied mapping.
- Record `isVariable: true` on each program-controlled node. Do not mark every node as a variable merely because it is a TextBlock, GameImage, or child widget.
- Record `properties.justification` on every text node. For dynamic single-line text, combine justification with an appropriate fixed edge and content-driven width so longer values grow into available space instead of covering protected content.
- Record `adaptiveLayout.horizontal`, `adaptiveLayout.vertical`, and a concise `adaptiveLayout.reason` for adaptive screen regions, independently adapting decoration, and children whose parent Slot alignment carries an edge or stretch decision. Keep it consistent with Canvas anchors/`slotLayout`, Overlay alignment, `flowSlot`, or `scrollSlot` as applicable; do not apply a Canvas top-left anchor model to non-Canvas children. Here `adaptiveLayout` describes edge/occupancy behavior inside the allocated Slot; it never selects Box main-axis allocation. `flowSlot.size` is authoritative, so `Auto` plus Alignment `Fill` is not weighted expansion.
- Lower each accepted `imageComposition` complete image to exactly one realization: normally one `visual.image` / GameImage node, or one verified `widget-tree-instance` relation when a shared control supplies that complete graphic. Never create a local image that duplicates a relation-backed shared visual. When `explicitImageOwnerIntentRequired` is enabled, map an inherited image's exact `ownerIntentId` to its owner node or nested-control relation, copy both accepted axes into that owner's adaptive contract, and prove the image remains structurally inside that owner through WidgetTree ancestry or a verified child/reuse host chain; do not choose another reachable ancestor at build time. A Button Backplate and glyph are normally separate complete groups when their surface/stretch and glyph/resource responsibilities differ, but never construct the glyph itself from point, line, corner, or color-fragment GameImages. An additional layer of the same graphic requires the accepted split reason from the Requirement.
- Set `profile.regionGrouping` from the image evidence. When true, mark every region container with a unique `regionPurpose`, keep ordinary content below a region ancestor, and use `rootLayer` only for genuine global backgrounds or overlays.
- Derive `profile.targetAsset.folder` and `profile.targetAsset.name` from the complete Widget Blueprint asset rules. Reject a system-folder mismatch before touching the Editor.
- In production mode, require `asset.folder/name` to equal `profile.targetAsset.folder/name`. In prototype mode, keep `asset` below `/Game/UI/AIPrototype`.
- Save the task spec under `<project>/Saved/CodexUILayout/<asset-name>.json` when filesystem writes are authorized.
- Run `python scripts/validate_layout_spec.py <spec>`.
- Fix every error before touching the Editor. Treat warnings as prototype review notes.
- Run `python scripts/select_rules.py <spec>` to load only applicable rules from [rule-index.json](references/rule-index.json).
- Apply selected rules in source order: `explicit` rules first, then `observed` reference patterns, then `baseline` prototype rules. Never let an observed pattern override an explicit rule; report conflicts.
- Load the directly linked reference file for every selected project or system-specific rule.
- Run `python scripts/prepare_build.py <spec> --output <plan>` to produce the deterministic MCP call plan. The planner revalidates the UILayoutSpec and refuses to emit a plan for an invalid `Desired` root or any other validation error.
- For a multi-step plan, first read `ProgrammaticToolset.get_execution_environment` and inspect the output schemas of every tool the generated script will call. Then prefer resumable batch execution: `python scripts/execute_plan_programmatic.py <plan> --checkpoint <checkpoint.json> --run-all`.
- `execute_plan_programmatic.py` records an atomic checkpoint after each completed chunk; use that checkpoint to resume a failed batch only after validating the same plan digest.
- Use the step-by-step fallback `python scripts/execute_plan.py <plan> --log <log>` only for small plans, diagnostics, or compatibility recovery. It requires the Python `requests` package and fails without mutating the Editor when it is unavailable.
- Before either execution command for a requirement-driven build, run `python ../analyze-nextgame-ui-requirements/scripts/validate_build_bundle.py <ui-build-bundle.json>` and `python ../analyze-nextgame-ui-requirements/scripts/validate_requirement_coverage.py <ui-build-bundle.json>`. These follow `bundle.requirement.path`; use `--requirement <ui-requirement.json>` only to override it. Do not use `--skip-linked-files` at this gate, because requirement/layout hashes and linked UILayoutSpec checks are required.
- If a validated Bundle contains `bootstrapSnapshot`, the first execution phase is limited to that new shared asset and its declared extension. Do not run any transitive Parent Class, nested, EntryClass, or screen consumer while activation remains `required`. Compile, save, read back, publish the actual active Registry entry with a compare-and-swap guard on the snapshot's base Registry digest/revision, replace `bootstrapSnapshot` with the real `registry` binding, mark activation `verified`, and rerun both strict validators before the second execution phase. Never carry `planned-bootstrap` or `activation.status: required` into completed/passed output.

### 3. Connect to Unreal Editor

- Require Unreal Editor to be running with `http://127.0.0.1:8000/mcp` available.
- Use the `unreal-editor` MCP dependency supplied by this plugin.
- Call `list_toolsets` only when discovery is needed.
- Use the server `call_tool` wrapper for toolset calls.
- Read [umg-mcp-workflow.md](references/umg-mcp-workflow.md) for exact toolsets and reference handling.
- Stop without partial Editor mutation if the MCP server is unavailable.

### 4. Build the Widget Blueprint

- Check whether the target asset already exists before creating it.
- Create only at the destination validated for the selected mode.
- Follow the generated plan in dependency order.
- Preserve each returned `refPath`; never invent transient Widget or Slot references.
- For every Widget, Slot, or UI component property write, call `ObjectTools.list_properties`, then `get_properties`, then `set_properties` using the exact returned names.
- Apply node-level `isVariable` through `UMGToolSet.UMGToolSet.ToggleWidgetAsVariable`; do not attempt to write protected `bIsVariable` through ObjectTools.
- Keep only catalog roles that are still explicitly marked as native placeholders native for this MVP, and record their substitution warning. This exception never applies to `visual.image`, which is already mapped to project `GameImage`.
- Set displayed passive components to `SelfHitTestInvisible`. Use `Collapsed` for an intentionally inactive runtime-controlled state branch; use `Hidden` only when preserving its layout allocation is deliberate and the accepted requirement supplies `preserveLayoutReason`. Preserve hit testing on controls and collection/scroll components that actually handle input.
- For wrapped text, set a positive explicit `wrapTextAt`; do not rely on a zero/default wrapping width.
- When text can grow, use flow layout or adaptive CanvasPanel Slot settings so related backgrounds and decorations follow the resulting content size.
- Treat `profile.targetAsset` as metadata only in prototype mode.
- In production mode, create or reuse the validated system folder and required `Widgets` subfolder, then create the asset exactly at `profile.targetAsset`.
- For fight work, prototype independent `uw_fight_*` feature modules and plan their placement in `umg_fight`; do not flatten feature controls into the integration screen.
- For a data-driven list, compile the `profile.listRole: entry` asset first and set the owning collection's `entryWidgetClass` to that generated class. A non-fight screen may own a screen-local collection directly; extract a separate collection module when the collection is an independent feature. Fight continues to integrate only the collection feature module. A fixed screenshot count does not justify authored duplicate rows when the repeated content is data or image driven.
- For `show-all` collections, make the nearest Canvas child follow desired size and verify that ancestors allow growth. When a TileView must preserve a fixed column count, constrain only its width with a one-child `SizeBox`, leave height override disabled, and auto-size the wrapper Canvas slot; use the real `SetWidthOverride`/`ClearHeightOverride` methods during Editor automation rather than assuming a raw property value enables the override.
- For every `LuaTileView`, create visible horizontal and vertical gaps by making `entryWidth` and `entryHeight` larger than the visible entry-content footprint. Keep `horizontalEntrySpacing` and `verticalEntrySpacing` at zero or omit them; those fields shrink the usable entry area inward and must not be used to widen the tile pitch.
- Name every SizeBox instance with the `Size` prefix and use it only for a concrete one-child size constraint. Activate the minimum set of exact, minimum, or maximum constraints, clear unused overrides through the matching Unreal methods, and do not substitute SizeBox for structural panels, ScaleBox, or a deliberate scroll viewport.
- Do not create, connect, or validate Lua, C++, or Blueprint business logic. Setting the required `Is Variable` flag is structural exposure, not business hookup. This tool's production responsibility ends with UMG assets, WidgetTree structure, variable flags, structural list-to-entry class assignment, properties, compile, save, and visual/structural verification. Project code implements behavior separately.
- Preserve the validated region hierarchy when adding widgets; do not re-flatten nodes during Editor mutation.
- For an accepted `exclusive-panel-branches` presentation, create all accepted state Panel subtrees. Set the initial active passive branch to `SelfHitTestInvisible`, inactive passive branches to `Collapsed` or justified `Hidden`, and expose each program-controlled branch root as a variable. Do not add state-switching EventGraph, Lua, or C++ logic.
- When an accepted state model is controlled by user interaction, mark its owning asset as interactive and place the complete visual state family beneath or alongside a hit-area `input.button` named `Btn*`. A selected/unselected or mode-switching entry without a Button input owner is incomplete even when project code will perform the actual state change.
- Use a shared tree only for an accepted `shared-tree-properties` state model whose topology remains identical. Keep every changed program-controlled node traceable in the bundle.
- For a child instance with `stateRefs`, record exactly one matching `crossAssetOperations[].stateHandling` strategy from [requirement-build-handoff.md](references/requirement-build-handoff.md): `owning-screen-state-tree`, `static-variant-asset`, `instance-parameter`, or `runtime-dependent`. Also enforce the reverse link: every state-handled target mapping names exactly one uniquely assigned requirement element, and its mapping refs, handling refs, and assignment refs match exactly. A runtime-dependent preview exclusion requires `previewExclusionReason` and an accepted structured deviation; it does not waive state coverage.
- Let a Button directly own a CanvasPanel when that CanvasPanel already supplies the required internal layering and placement. Insert an Overlay only when it has a documented shared-bounds, independent-alignment, or multi-layer purpose; do not generate a purposeless `Button -> Overlay -> CanvasPanel` chain.
- A direct `Button -> CanvasPanel` content host must declare `buttonSlot` in the UILayoutSpec with `padding: [0, 0, 0, 0]`, `horizontalAlignment: "Fill"`, and `verticalAlignment: "Fill"`. The validator and generated plan reject omitted or non-Fill contracts. Preserve a non-zero inset only by using a different, explicitly designed internal layout rather than silently shrinking the direct content host.
- Give every direct Overlay child an explicit `overlaySlot` horizontal and vertical alignment. When that child covers the Overlay's complete rectangle, use `Fill` on both axes; use non-Fill alignment only for intentionally local-sized or independently aligned layers.
- Give every direct VerticalBox/HorizontalBox child an explicit `flowSlot` with Size, Padding, Horizontal Alignment, and Vertical Alignment. Size controls allocation on the Box main axis; Alignment controls how the child occupies that allocation. A content-driven child uses Size `Auto` even when either Alignment is `Fill`. Use Size `Fill` with an explicit positive weight only when the child must consume weighted remaining space.
- Give every direct GameScrollBox child an explicit `scrollSlot` with Padding and both alignments. Choose them from the child's measured size, owning-region intent, scroll direction, and desired cross-axis behavior; do not copy a default alignment or invent a flow Size field that ScrollBoxSlot does not own.
- When integrating a child asset whose local reference size differs from its screen host rectangle, select and record an explicit host strategy: Canvas Fill/stretch, flow sizing, or a purpose-built ScaleBox. Do not infer host geometry from child `referenceSize`; do not use a placeholder `ReplaceWidgetWithTemplate` operation as a formal child integration.
- Complete the final structural compile, but do not save yet; the generated-class CDO Designer mode is written in the next step and both changes are saved together.
- After the final structural compile and before save, get the generated `UUserWidget` class default object, confirm the exposed `designSizeMode` property through ObjectTools list/get, set the reviewed `FillScreen|Desired` value, then save. Do not write the property on the WidgetBlueprint asset object. After save, reacquire the generated CDO and read the property again; a plan value or an earlier read is not final evidence. For a reuse-only system child, modify and verify only that child CDO, never the shared parent merely because it is consumed.
- If the official ObjectTools route cannot expose or set this editor-only protected CDO property, record that exact limitation and use the allowed NxUE fallback `manage-property` against `/Game/.../<Asset>.Default__<Asset>_C`, with `propertyPath: DesignSizeMode`; save the WidgetBlueprint asset and read the same CDO property again. For mixed acquisition, bind that fallback evidence to the exact `$.assets[i].designSizeMode` readback path. Do not use a Slate click as production evidence and do not silently fall back to `ThumbnailSizeMode`.

## Safety boundaries

- Do not claim pixel-perfect reproduction.
- Do not create or modify C++ classes.
- Do not infer undocumented project standards.
- Do not write to a production folder without explicit authorization.
- Do not create a production asset at a location different from the validated formal target.
- Do not overwrite or delete an existing asset without explicit authorization for that exact asset.
- Do not silently substitute native controls after a project component mapping is later added.
- Do not treat the requirement-review approval, an earlier blanket request, or Agent inference as post-build user acceptance.
- Do not describe the full requirement-driven production flow as complete while a required documentation stage remains incomplete, unless the user explicitly excluded that stage.
- Keep stable node IDs so reruns can update instead of duplicate once the batch builder supports idempotent updates.
- Treat every shared-registry asset as read-only unless the user explicitly authorizes updating that exact asset; choosing it for reuse does not authorize changing the shared parent.
